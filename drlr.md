OpenCode is an open-source AI programming agent that automates software development tasks by interacting with code repositories, executing shell commands, and managing projects and user sessions. It provides AI agents with the ability to understand, generate, and modify code, streamlining development workflows.

The system offers various interaction points and key functional capabilities:

User Interfaces: Access is available via a command-line interface (packages/cli), a web application (packages/app), and a dedicated Electron-based desktop application (packages/desktop).
AI Agent Execution: A confined JavaScript execution environment, CodeMode (packages/codemode), securely orchestrates AI model operations and tool calls. It allows AI models to sequence dependent tasks, filter results, and perform data transformations.
Core System Operations: The core system logic (packages/core) manages configuration, AI SDK integrations, and data persistence using Drizzle ORM. It handles in-process background jobs and filesystem utilities.
Development Workflow Automation: OpenCode integrates with GitHub workflows (github) to automate responses, execute Git operations, and manage issues within repositories.
API and Data Management: Extensible API specifications define project and session management (specs). The infrastructure (infra) supports deployment, monitoring, and a data lake for analytics.

Development methodologies are underpinned by defined architectural and coding standards. Localization and Translation Workflow
The project employs a robust strategy for multilingual support, integrating locale-specific glossaries, automated translation commands, and strict guidelines for UI and documentation translation. This approach ensures consistency and cultural appropriateness across all localized content.

The foundation of the localization workflow lies in a decentralized system of locale-specific glossaries, managed in the .opencode/glossary directory. These glossaries, like .opencode/glossary/ar.md for Arabic or .opencode/glossary/ja.md for Japanese, provide detailed guidance for translators beyond a global set of rules. They specify terms that must remain untranslated (e.g., product names like OpenCode or technical acronyms like CLI), preferred translations for recurring UI terms, and general advice on maintaining natural phrasing and tone. For example, .opencode/glossary/no.md explicitly lists preferred Norwegian Bokmål terms like Lagre for "Save," while .opencode/glossary/zh-cn.md provides preferred Simplified Chinese terms such as 提示词 for "prompt." The .opencode/glossary/README.md outlines the structure and contribution guidelines for these files, ensuring that community-driven linguistic preferences are captured and maintained.

Automated translation commands are a core component of this strategy, streamlining the localization process. The .opencode/command/translate.md describes a command designed to translate English text from Git diffs into multiple international languages in parallel. This command is crucial for documentation and UI copy, enforcing the preservation of meaning, intent, tone, formatting, and technical terms. It strictly adheres to "Do-Not-Translate" glossaries and locale-specific guidance, while explicitly preventing modifications to fenced code blocks. Further automation is evident in script/translate-app.ts, which orchestrates AI-assisted translation of application, UI, and desktop localization files. This script identifies "drift" (missing or mismatched translations), prepares prompts for the AI, executes translation tasks, and validates the results, ensuring high-quality and consistent output. The accompanying script/translate-app.md provides strict guidelines for translating product application locales, emphasizing the preservation of English intent and specific rules for handling keys and placeholders.

The emphasis on stringent guidelines extends to all aspects of translation. The glossaries in .opencode/glossary not only define preferred terms but also offer "Guidance" on achieving natural phrasing and "Avoid" sections to prevent common errors, such as literal translations or mixing terms for the same concept. This comprehensive approach ensures that the localized versions of the application and its documentation are not merely translated but are culturally appropriate and maintain the original intent and clarity.

CLI Application and Daemon Services
The lildax command-line interface (CLI) is the primary text-based interface for interacting with the OpenCode system. Its development encompasses a build and publishing process, a structured framework for defining commands, and a runtime environment that includes a critical background daemon service.

The CLI's build process, managed by scripts such as packages/cli/script/build.ts, compiles the TypeScript source into platform-specific binaries for various operating systems and architectures. This process dynamically injects build-time constants, such as version and channel information, directly into the compiled code. Following the build, the packages/cli/script/publish.ts script automates the publication of these binaries to npm, along with a main CLI package. This script ensures that each package is published only if it is a new version and leverages optionalDependencies to link the platform-specific binaries to the main CLI package.

At its core, the lildax CLI uses a declarative framework for command definition, primarily located in packages/cli/src/framework. Commands are defined using a Spec structure, as seen in packages/cli/src/commands/commands.ts, which separates the command's structure and configuration from its execution logic. This framework supports nested subcommands and utilizes Argument and Flag for defining command-line arguments and options. The execution of these commands is managed by a runtime environment, detailed in packages/cli/src/framework/runtime.ts, which integrates with the effect library for handling asynchronous operations and managing side effects. This integration ensures robust error handling and dependency injection, supporting lazy loading of command handlers to optimize startup performance.

A central component of the lildax CLI is its background daemon service, managed within packages/cli/src/services/daemon.ts. This daemon acts as a backend, providing services such as API interaction, authentication, and status monitoring. The daemon's management includes functionalities for starting, stopping, and registering the service, as well as handling secure password management for client communication. The CLI interacts with this daemon to perform many of its operations, ensuring that tasks can be executed persistently and asynchronously. The daemon's state, including registration information and passwords, is persisted to files within a designated state directory, and communication is secured through shared secrets.

The CLI also features a Terminal User Interface (TUI), initiated by the runTui function in packages/cli/src/tui.ts. This TUI is configured to interact with the daemon service, providing a user-friendly interface within the terminal. A notable feature of the TUI's interaction with services is its gracefulFetch implementation, which can handle 404 responses by providing predefined fallback data, ensuring a smoother user experience even when certain resources are unavailable.

The overall initialization and execution of the CLI application, orchestrated by packages/cli/src/index.ts, involve providing necessary services, such as the daemon and Node.js-specific functionalities, to the application's runtime. This setup ensures that the lildax CLI is a robust, extensible, and user-friendly interface for the OpenCode system.

Client Libraries and API Interaction
The OpenCode project provides client libraries for interacting with its HTTP API, offering both Promise-based and Effect-based clients. These libraries are designed to ensure type safety and consistent error handling across client-server communication. The API contract generation process is central to maintaining this consistency.

The project utilizes a build compiler that reads the API definition from the server-side, generating client-side API code. This process ensures that the client's understanding of the API remains synchronized with the server's implementation, preventing discrepancies that could lead to runtime errors. An equivalence test is also in place to detect any "transport drift" between the client and server.

There are two primary client entry points:

A standard Promise-based HTTP client, found in packages/client, offers a straightforward approach to API interaction using fetch. This client is designed for simplicity, without dependencies on the Effect runtime.
An Effect-based client, located within packages/client/src/generated-effect, provides a more feature-rich experience for consumers leveraging the Effect library. This client expects an environment-provided HttpClient and uses canonical decoded values such as Session.ID and Location.Ref from the project's schema package.
The API contract itself is defined in packages/client/src/contract.ts. This configuration combines a default API with custom middleware, such as LocationMiddleware and SessionLocationMiddleware, which handle location and session-specific concerns during API requests, including error handling for invalid requests or missing sessions. The contract also specifies how endpoints are grouped, renamed, and which endpoints should be omitted from the client API. For instance, specific server-side functionalities might be excluded from the client due to security or architectural considerations.

Type definitions for all API inputs, outputs, and errors are centralized in packages/client/src/generated/types.ts. This file exports numerous TypeScript type aliases and corresponding type guard functions for robust error handling and type narrowing. Error handling is further standardized through the ClientError class, defined in packages/client/src/generated/client-error.ts, which categorizes failures into distinct reasons like "Transport" or "UnexpectedStatus". The Effect-based client uses a similar ClientError type, detailed in packages/client/src/generated-effect/client-error.ts, which can wrap underlying "defects" for more granular error reporting.

The packages/client/src/index.ts file serves as the primary entry point for the client libraries, re-exporting all symbols from the generated Promise-based client and aliasing specific types for ease of use. Similarly, packages/client/src/effect.ts aggregates and re-exports Effect-related data types and schemas, ensuring a strict separation from core or server modules.

Confined AI Model Execution Environment (CodeMode)
CodeMode is a secure, confined JavaScript execution environment designed to empower AI models with sophisticated orchestration capabilities. It allows AI agents to sequence dependent tasks, run concurrent tool calls, filter and aggregate results, and perform data transformations using a host-provided set of tools. This environment is crucial for enhancing AI agent efficiency by reducing redundant interactions with external systems, keeping intermediate results localized, and ensuring that AI-generated code operates within explicitly defined security boundaries. The fundamental principle of CodeMode is to provide an orchestration language for AI, not a general-purpose JavaScript runtime, meaning it intentionally limits access to ambient system resources like filesystems or networks unless explicitly granted through defined tools.

At its core, CodeMode utilizes an owned tree-walking interpreter, as detailed in the packages/codemode/src/interpreter directory, to execute a bounded subset of JavaScript. This approach ensures that the execution environment is tailored precisely to the needs of tool orchestration, maintaining tight control over language features and behaviors. The interpreter processes transpiled TypeScript, generating an Abstract Syntax Tree (AST) that is then executed in a secure sandbox. This sandbox prevents unauthorized access to host features and enforces execution limits such as timeoutMs, maxToolCalls, and maxOutputBytes, configurable through packages/codemode/src/codemode.ts, to prevent resource exhaustion and manage program complexity.

CodeMode also incorporates a sandboxed standard library, with its implementations residing in packages/codemode/src/stdlib. This library provides secure versions of common JavaScript functionalities, ensuring that operations like date manipulation, regular expression matching, and URL parsing occur within the confined environment without exposing underlying system resources. This careful construction of the standard library is vital for maintaining the security and predictability of AI-generated code execution.

A key capability of CodeMode is its robust tool orchestration mechanism. Tools are defined with clear input and output schemas, which can leverage either Effect Schema or JSON Schema. These definitions, created using Tool.make as described in packages/codemode/src/tool.ts, ensure type safety and explicit data contracts between the AI model and the host system. The system manages tool discovery and cataloging, presenting a token-budgeted catalog to AI models and offering a searchable tool registry ($codemode.search) for comprehensive access to available functionalities. This mechanism is primarily managed by the ToolRuntime in packages/codemode/src/tool-runtime.ts.

Furthermore, CodeMode includes powerful OpenAPI integration, allowing it to automatically generate callable tools directly from OpenAPI 3.x specifications. Cross-Environment Secret and Configuration Management
The AnomalyCo OpenCode project centralizes the management of application secrets and environment-specific configurations to maintain consistency and security across different deployment stages. This approach ensures that sensitive information is handled securely and that application settings adapt dynamically based on the deployment environment.

Environment-specific configurations, such as domain names, are dynamically determined by the application's stage. For instance, the domain variable within infra/stage.ts will resolve to opencode.ai for the production environment, dev.opencode.ai for the development environment, and ${$app.stage}.dev.opencode.ai for other stages. This dynamic resolution extends to shortDomain, which provides abbreviated versions of these names. Cloudflare DNS records are also configured within infra/stage.ts, specifically for the "production" stage, including CNAME and TXT records for trust.opencode.ai, ensuring proper domain verification and routing. A cloudflare.RegionalHostname is consistently created across all stages, linking to the determined domain.

Secure management of application secrets is handled through sst.Secret constructs, as defined in infra/secret.ts. This file declares various sensitive parameters like R2AccessKey, HoneycombApiKey, and UpstashRedisRestToken. For certain secrets, such as HoneycombWebhookSecret, a random.RandomPassword is employed to generate secure, random strings, further enhancing security by avoiding hardcoded values. These generated secrets are then wrapped using sst.Linkable.wrap to make them accessible within the sst framework, ensuring that all components can securely access necessary credentials without exposing them in code. This system allows for sst.Secret instances to be linked to other resources, such as the api worker in infra/app.ts, making them available as environment variables.

The overall infrastructure, spanning API deployments, documentation, web applications, and console services, leverages these centralized configurations and secrets. For example, the infra/app.ts file uses dynamically resolved domain values for configuring subdomains like api.${domain}. Similarly, the console application defined in infra/console.ts integrates with various secrets (e.g., GITHUB_CLIENT_ID_CONSOLE, STRIPE_SECRET_KEY) managed through this system. This integrated approach ensures that the application behaves predictably and securely across development, staging, and production environments, adapting its behavior and access credentials as needed. TUI Extraction and Standalone Package Refactoring
The Terminal User Interface (TUI) is being refactored into an independent workspace package, packages/tui, within the opencode repository to ensure a single, canonical implementation usable by both legacy and new command-line interfaces. This refactoring effort is structured into a ten-section migration plan, as detailed in specs/tui-package.md.

The plan begins by establishing a basic package skeleton for packages/tui, defining its package.json, tsconfig.json, and initial dependencies to enable independent development and testing. Subsequent steps focus on migrating low-coupling UI elements, such as presentation utilities, themes, keybinding mechanics, and UI primitives, into this new package.

A key aspect of this refactoring involves decoupling backend tools from the TUI. Tool rendering will be updated to rely solely on SDK wire data, removing direct imports from backend tool implementations. This ensures that the TUI interacts with backend functionality through a well-defined interface, treating tool input and metadata as opaque data structures with local type guards. This approach reinforces the SDK as the exclusive boundary for OpenCode interaction within the TUI, preventing direct dependencies on internal backend implementation modules.

The migration also explicitly addresses runtime inputs, replacing reliance on process-global state with immutable runtime inputs like TuiCapabilities, TuiPaths, and TuiBuildInfo, which are passed directly to the TUI. Configuration schemas, defaults, and keybinding resolution will also be moved to packages/tui, while file discovery and precedence remain with the host CLI.

Further steps involve relocating SDK client providers, event synchronization, routes, and session views into packages/tui, solidifying the SDK as the single source for OpenCode domain data and operations. Plugin presentation aspects, including plugin slots and TUI-facing APIs, are isolated within packages/tui, ensuring that the TUI manages how plugins are displayed and interacted with, while plugin discovery and activation remain host responsibilities.

The final stages of the plan convert both legacy and new CLIs into thin adapters that consume the public packages/tui API to launch the TUI. This allows the CLIs to retain their host-specific duties (e.g., command parsing, server management) while leveraging the centralized TUI implementation. The process concludes with the removal of temporary compatibility shims and obsolete code, ensuring packages/tui is a fully self-contained package with no direct imports from other OpenCode implementation packages. This strategy promotes clear ownership boundaries and enables incremental, independently verifiable changes throughout the migration.

OpenCode V2 API, Architecture, and Plugin System
The OpenCode V2 API and its underlying architecture represent a significant evolution towards a more modular, extensible, and robust system. This version introduces a plugin-oriented design, refined context management, and a flexible policy system to govern resource usage. The core goal is to enable dynamic behavior, hot-reloadability, and a clear separation of concerns, moving away from monolithic services towards a set of interconnected, event-driven components.

The V2 API (specs/v2/api.html) is structured around a central concept of Context Models, which define how API calls derive their operational context (server-scoped, request-context, or session-pinned). This ensures that each operation (Endpoint Inventory) is executed within the appropriate runtime environment. The API adheres to a single /api route surface, treating HTTP routes as mounts for RPC-style operations, which simplifies client interaction and promotes a unified approach to service communication. Data synchronization for frontend applications is managed through a SyncStore model, designed to maintain a consistent view of the server state.

A fundamental shift in the V2 architecture is the emphasis on a plugin-oriented design (specs/v2/instructions.md). The packages/core module is refactored to house domain schemas, typed errors, state containers, and event definitions, but crucially, it delegates complex application logic and integration-specific behavior to plugins. Core services within packages/core are designed as "dumb containers" that manage state with minimal operations (e.g., get, update) and trigger hooks for plugins. This design promotes decoupling, modularity, and extensibility, allowing for dynamic modifications and hot-reloading without full process restarts. Plugins extend core functionality via PluginV2.HookSpec, which receive immutable input and mutable Immer drafts, enabling them to enrich, cancel, or validate changes to the system. This plugin-centric approach is also reflected in how catalog state changes and plugin lifecycles are managed, favoring a granular approach where the Catalog directly processes transformations rather than relying on broad service reloads (specs/v2/catalog-config-plugin-lifecycle.md).

Provider and model management (specs/v2/provider-model.md) are integral to the V2 system. Schemas are defined for ProviderV2 and ModelV2, capturing their identifiers, configuration options, endpoint types, capabilities, and cost/limit details. This structured approach allows for robust management of various AI models and their respective providers. The system defines a clear interface for interacting with the provider and model catalog, including methods for retrieving, filtering, and transforming provider and model information. The plugin system further extends this, enabling providers to register themselves as plugins, thus integrating seamlessly into the dynamic model registration process.

To control resource access and behavior, V2 introduces a sophisticated policy system (specs/v2/provider-policy.md). This system defines PolicyInfo statements with effect (allow/deny), action, and resource to govern operations, primarily focusing on provider.use. Policies replace legacy enabled_providers and disabled_providers configurations with a more flexible framework that supports wildcard matching and order-dependent evaluation. This allows for granular control over what operations are permitted on specific resources, enhancing security and configurability. The policy system ensures a clear separation between configuration and enforcement, allowing for robust governance without embedding policy logic directly into component configurations.

Session management (specs/v2/session.md) in V2 is also significantly enhanced. It defines mechanisms for creating sessions, submitting prompts, and handling execution, with a strong emphasis on durable event sourcing. Context Epochs are introduced to persist System Context, ensuring immutability and providing chronological updates. Automatic compaction dynamically manages context windows for models, replacing older history with summaries to optimize token usage while retaining the full transcript durably. A SessionRunCoordinator serializes execution for individual local sessions while allowing concurrent execution across different sessions. The Tool Registry provides a Location-scoped mechanism for defining and registering locally executable tools (specs/v2/tools.md), complete with input/output schemas, execution contexts, and robust failure semantics. This allows for the creation of application tools, built-ins, and plugin tools that interact with the system in a controlled and predictable manner.

Finally, the V2 roadmap includes ongoing efforts for backend cleanup, a new data model for subagents and skill invocations, and further enhancements to the agent loop (specs/v2/todo.md). The system is designed to be hot-reloadable, with services emitting granular events to enable dynamic reactions and reconfiguration without requiring full restarts. This emphasis on event-driven architecture and plugin-based extensibility aims to create a highly adaptable and resilient platform. Schema changes for V2, detailed in specs/v2/schema-changelog.md, document modifications across databases, events, and APIs, providing a comprehensive overview of the evolutionary path of the platform.

The project employs a hypothesis-driven optimization algorithm to enhance test suite efficiency, as detailed in perf/test-suite.md. This structured process involves several key stages to identify bottlenecks, formulate and test hypotheses, and evaluate their impact.
